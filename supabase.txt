## Recommended additions

These are **proposed additions**, not tables currently present.

### Highest priority

1. **`organization_memberships`** — Connect Supabase Auth users to organizations and roles: `organization_id`, `auth_user_id` (references `auth.users.id`), optional `branch_id`, `role`, `status`, `created_at`; unique on `(organization_id, auth_user_id)`.  
   Your `public.users` table has no Auth-user ID link. This membership table would give RLS a reliable way to determine which organizations a signed-in user belongs to.

2. **`parts_catalog`** — A canonical record for each part, such as organization, part number, name, category, compatible models, barcode, and active status. `branch_inventory` can then refer to a catalog item instead of duplicating part descriptions for each branch.

3. **`inventory_movements`** — An append-only stock ledger recording part, branch, quantity change, movement type, reference to the sale/receipt/transfer, actor, and timestamp. This makes stock changes auditable; `stock_quantity` alone doesn’t explain how stock changed.

4. **Procurement and receiving:**  
   - `suppliers`: supplier identity and contact details.  
   - `purchase_orders` and `purchase_order_items`: what was ordered, from whom, and at what cost.  
   - `goods_receipts` and `goods_receipt_items`: what physically arrived and how it relates to the order/container.  
   
   `inbound_containers` tracks shipments, but it does not list the parts or quantities inside them.

5. **`customers`** — Reusable customer records linked from orders and WhatsApp threads, rather than relying on phone-number or free-text fields in multiple tables.

### Add if those workflows are required

- **`sales_payments`** for split, partial, or multiple tender payments per order.
- **`sales_returns` / `sales_return_items`** for refunds, exchanges, and returned stock.
- **`branch_transfers` / `branch_transfer_items`** for tracking inter-branch stock movement. Dispatch manifests describe deliveries but don’t specify the transferred parts and quantities.
- **`payout_recipients`** if payout recipients need stable records and links to mechanics or staff.

## Important RLS gap

RLS is enabled on all 19 current tables, but the live schema shows explicit policies on only `branch_inventory`, `sales_orders`, `daily_expenses`, and `eod_reconciliations`. Those policies use the custom setting `app.current_organization_id`; the script you shared uses a different setting name. Before exposing these tables to clients, define policies that match the actual columns and derive organization access from authenticated membership. Supabase recommends enabling RLS on exposed tables and limiting policies to the roles and operations that need access. See the [Supabase RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security).

Also, because tables independently store `organization_id` and `branch_id`, add constraints or other safeguards to ensure a row’s branch belongs to the same organization as the row. The recommendations above are a design outline, **not a ready-to-run migration**; a migration should be prepared against the desired workflows and reviewed before applying.
